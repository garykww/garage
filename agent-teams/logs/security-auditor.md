## 2026-07-01 22:54 — Follow-up review: billing-code-agent's fix for Get()/lineItems bypass and Total() int64 overflow
**Assigned by:** direct request (asked to independently re-verify billing-code-agent's follow-up fix to two prior findings: [High] exported Invoice.LineItems + live-pointer Ledger.Get bypassing AddLineItem/AddSaleLineItem validation, and [Medium] Total's unbounded int64-cents accumulation with no overflow check)
**Findings:**

Confirmed both files declare `package billing` (billing.go:5, billing_test.go:1) — billing_test.go is an internal test, not `package billing_test`, so it can reach unexported fields directly; that access does not represent the external-caller threat model, but the regression tests still validate the copy semantics that protect external callers too (see below).

1. **[Pass] Get()/lineItems bypass — closed for external callers.** `Invoice.lineItems` is now unexported (billing.go:35), so any caller outside package `billing` cannot write `inv.lineItems = append(...)` at all — it's a compile error. `Ledger.Get` (billing.go:92-100) now returns a value copy of the Invoice with an independently-copied `lineItems` slice (billing.go:97-98), and `Invoice.LineItems()` (billing.go:43-47) returns a second defensive copy on top of that. The only append into the live slice happens inside `AddLineItem` (billing.go:141), which runs full validation first. `TestGetReturnsCopyNotLiveInvoice` (billing_test.go:444-483) exercises the copy semantics via same-package field access (the only way an in-package test *can* exercise it, since the compile-time field-access bypass no longer exists to reproduce) and correctly proves mutating the returned copy — including `lineItems` and `Status` — never reaches the ledger's stored invoice. This closes the original [High] finding for the actual threat model (external callers via the public API).
   - Residual/new, Low: `Ledger.CreateInvoice` (billing.go:63-67) still returns the *same* live `*Invoice` pointer stored in the map (`inv := &Invoice{...}; l.invoices[id] = inv; return inv`), asymmetric with `Get`'s now-documented copy contract. `lineItems` is protected by unexported-field compilation, so this doesn't reopen the line-item bypass, but an external caller holding the value from `CreateInvoice` can still write `inv.Status = "paid"` directly, bypassing `MarkPaid` with no validation and no ledger-side record of who/when. Worth a doc note or making `CreateInvoice` return a copy too for consistency, but not itself a financial-integrity bug since `Status` has no invariants Total()/etc. depend on.

2. **[Pass] Total() overflow detection — correct, including the multiply-before-accumulate step.** Per-item conversion is `cents := int64(math.Round(li.Amount * 100))` then `itemCents := cents * int64(li.Qty)` (billing.go:209-210). Given `AddLineItem`/`AddSaleLineItem` enforce `0 <= Amount <= MaxLineItemAmount` (1e9) and `0 < Qty <= MaxLineItemQty` (1e6) before any LineItem can enter `inv.lineItems`, `cents` is bounded by ~1e11 and `itemCents` by ~1e17 — nowhere near int64's ~9.22e18 ceiling, so the multiplication itself cannot overflow; only summing many such items across the loop can. The accumulation check (`newTotal := totalCents + itemCents; if itemCents > 0 && newTotal < totalCents { return error }`, billing.go:211-214) correctly relies on all contributions being non-negative (guaranteed by the validated Amount>=0/Qty>0 invariant), so a wrap manifests as the sum failing to increase — the check catches every such wrap. Verified the ~93-item wrap-point arithmetic in the code comment (billing.go:191-201) independently: int64 max / ~1e17 per max-magnitude item ≈ 92.2, matching `TestTotalRejectsIntegerOverflowFromManyLineItems`'s use of n=200 (billing_test.go:497-518) as a comfortable margin past that boundary.
   - New, Low, out of the original two findings but found during this pass: the final `return float64(totalCents) / 100` (billing.go:217) converts an int64 cent count to float64, which loses integer precision once `totalCents` exceeds 2^53 (~9.007e15 cents, i.e. ~$90.07 trillion) — well below the ~$92.2-quadrillion int64-overflow ceiling the new check guards. A single line item at `MaxLineItemAmount * MaxLineItemQty` already produces ~1e17 cents, past that precision threshold on its own. This means a legitimately-validated, non-overflowing invoice at the extreme end of the allowed range can still get a silently-imprecise (not overflowed, not erroring, just rounded-in-the-float-conversion) `Total()`. Pre-existing design choice (Total returning float64 predates this fix), not a regression from this change, but flagging since it sits right next to the overflow work just done. Remediation if ever relevant: return total cents as int64 (or a decimal/money type) rather than float64, or at minimum document the ~$90T precision boundary alongside the existing overflow-boundary documentation.

3. **[Pass] No other path reaches `inv.lineItems` unvalidated.** Grepped every method touching `lineItems`/`inv.` in billing.go: `AddLineItem` (billing.go:141) is the sole append site; `MarkPaid` (billing.go:242-249) only touches `Status`; `RenderInvoiceHTML` (billing.go:273-300) and `Total` (billing.go:202-218) only read; `Get` (billing.go:92-100) and `LineItems()` (billing.go:43-47) only copy-out. `ApplyLateFee` (billing.go:225-238) computes its fee and routes it through `AddLineItem`, so it's still gated by the same validation (including the pre-existing +Inf/NaN `feePercent` edge case, where a NaN/Inf `feePercent` produces a NaN/Inf `fee` that `AddLineItem`'s `IsNaN`/`IsInf` checks reject downstream — not a bypass, just worth knowing the guard is one layer removed from `ApplyLateFee` itself).

4. **[Pass] MarkPaid still persists correctly.** `MarkPaid` (billing.go:242-249) calls the internal `l.get` (billing.go:74-80), which returns the ledger's live pointer, and mutates `inv.Status` on it directly (billing.go:247) — this is the same pointer stored in `l.invoices`, so the mutation is visible to the ledger immediately and to any subsequent `Get`/`Total`/`RenderInvoiceHTML` call. `TestMarkPaid` (billing_test.go:291-301) confirms this round-trips through the now-copying `Get`. No regression: `Get`'s copy-on-read only affects callers reading a snapshot, not the ledger's internal mutation path.

**Decision:** Both original findings ([High] Get/lineItems bypass, [Medium] Total int64 overflow) are resolved as reported; confirmed with independent line-by-line tracing rather than trusting the summary. Two new Low-severity, non-blocking observations surfaced during the full re-read (CreateInvoice's live-pointer asymmetry with Get; Total's float64 conversion precision ceiling below the overflow ceiling) — reporting them for the record but not treating either as a regression of this fix or as blocking.
